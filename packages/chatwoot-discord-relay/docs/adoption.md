# Conversation ownership cutover and rollback

This is a maintenance operation requiring the owner's separate deployment authorization. Do not run it as an ordinary version update. The namespace names are stable: `conversation:v1:<account>:<conversation>`, `thread:v1:<thread>`, `account:v1:<account>`, `forum:v1:<forum>`, and `digest:v1:<channel>`. Each installation has independent namespaces. Never point a second installation at these namespaces.

## Private operator artifact

Use an operator artifact built from the **reviewed preservation change**, not the already published 0.31.0 operator (which lacks receipt handover). Its emitted `chatwoot-discord-relay/operator` module exports `LegacyArchive`, `scanPage`, `legacyScanPage`, `escalationBaseline`, `nextReceiptPosition`, `receiptSeal`, `validateReceiptPage`, `verifyAdoptionLinks`, `verifyLinks`, `validateCut`, `cutSchema`, `prepareAdoption`, `importAdoptionPage`, `sealAdoptionHistory` and `stageAdoption`. No new version is implied by this runbook.

The package includes [operator.ts](operator.ts) and [operator.config.ts](operator.config.ts), a private Durable Object RPC service and binding template. Copy them into a separately reviewed operator project, rename the configuration to `cloudflare.config.ts`, and use its standard Cloudflare Vite setup. Replace every placeholder identity and CONFIG from the sealed installation configuration. `LEGACY_HUB` references the original source namespace and object `global`; the partition bindings reference the target relay namespaces. After settled old-executor retirement, that source must run the separately reviewed frozen shell below. Neither a fresh Hub nor a namespace copy is a source.

Bind a trusted private client with `bindings.durableObject({worker:"relay-adoption-operator",exportName:"RelayAdoptionOperator"})`. Disable routes, workers.dev and preview URLs; the template's HTTP handler always returns 404. Never bind it to online ingress. The private service exposes `sourceIdentity`, `open`, `collect`, `baselinePage`, `disposition`, `auditNext`, `inventory`, `receiptPage`, `receiptSeal`, `auditPage`, `escalationBaseline`, `verify`, `prepare`, `importPage`, `seal` and `stage`. Source reads have a ten-second caller deadline which does **not cancel** a DO/SQLite invocation; online control deadlines are unchanged. Discord checks use the normal scoped limiter and durable cooldown reports.

Keep backups, titles, receipt pages and manifests in access-controlled **private artifacts**, never application logs, shell tracing, tickets or public build output. Titles can contain customer text even though receipt pages contain no message bodies, cached credentials or webhook tokens. Operator errors deliberately omit page/header values. Preserve an identical artifact when retrying a lost RPC receipt. Remove the private operator after separately authorized close-out.

## Actual live 0.27 source access

**Stock 0.27.0 has no inventory/export RPC.** No current live export access is assumed. A private binding cannot read another DO's SQLite. The minimum supported extraction path is [legacy-source-bridge.ts](legacy-source-bridge.ts), a source-only frozen `Hub` shell from the reviewed preservation artifact. It preserves the actual Worker name and Hub namespace/lifecycle and reads schema9 directly without constructing Store, applying migrations, creating indexes, dropping guards, or executing legacy jobs. Its HTTP handler refuses admission, it has no cron/admission methods, and alarms only delete their alarm. It does not inherit/rebuild the old executor.

This requires a **separately reviewed maintenance deployment** after a settled source boundary. Before that deployment, keep the existing 0.27 executor and its evidence intact: obtain a private backup, retain old ingress/request/interaction/routing evidence, establish an external admission refusal, pause upstream creation/delivery and old cron admission, and let existing old requests/alarms finish. Stock 0.27 has no new `cutover.phase` gate; do not feed new CONFIG to its strict parser. Version replacement, a changed webhook URL, an alarm deletion, or an empty queue does not cancel/prove absence of in-flight calls. If settled request/alarm evidence is unavailable, stop; this shell cannot reconstruct it. No final scans are supported while the old executor is active.

**Rollout hold for stock 0.27:** it deletes command jobs before execution, prunes interaction rows after an hour, and records neither a complete invocation ledger nor deleted Discord IDs. An empty queue, elapsed time, ordinary completion logs or a caller-supplied `drainEvidence` cannot establish settlement. Keep two independent private worksheets: (1) producer pause/late-event retention acknowledgements, accepted-request and alarm completion coverage correlated to the old version/object and fence epoch, and an obtainable immutable backup; (2) each unresolved baseline's exact digest plus a pre-loss receipt/deletion ledger, or explicit missing evidence. Verify actual provider trace coverage, retention, alarm coverage, backup exportability and pause semantics; none is assumed available here. If either required worksheet is incomplete, preserve the old executor/source and digests and stop before shell replacement, freezing or retirement.

A separately reviewed instrumented handover can only contain and observe **new** work after an independently evidenced fence/drain, and invalidate a boundary if later writes occur. It cannot retroactively certify old invocations or recover never-recorded/lost IDs. Such a deployment is a separate preparation decision, not a recovery implemented by this shell.

Build the source shell with only the original Hub lifecycle, private binding access, no scheduled events and no public relay handler. Review the prebuilt dry-run plan and verify the actual namespace/object `global`. Obtain the actual object id with the private operator `sourceIdentity()` using its verified original namespace binding, rather than guessing it from Worker names. Deploy `LEGACY_EXPORT_BOUNDARY` as `{sourceIdentity:<actual Hub DO id>,epoch:<immutable cut epoch>,drainEvidence:<private settled evidence reference>,frozen:true}`. The shell refuses export if this binding is absent or differs from the request or real DO id. Wait for explicit retirement/settling of every old invocation before collecting. Keep the schema9 source and all guards throughout staging and observation; retiring execution is distinct from deleting source data. If the subsequent source audit finds pending jobs/unknown guards, preserve them and stop the cut for disposition; the shell never silently executes or discards them. Target adoption begins only after this evidence and complete export exist.

If a different source version or patched implementation is actually deployed, or the old request evidence cannot establish a settled boundary, stop for review. A missing/ambiguous authoritative record blocks the preservation cut. Do not fabricate it from Discord content, timestamps, history similarity, Chatwoot links or a guessed watermark.

## Inventory from the retained frozen source

1. Verify Worker/Hub identity and schema (0.27 schema9; supported schema10). Open one private archive per immutable frozen boundary. `collect(source,after)` reads one table's indexed rowid range of at most 100 rows and persists it atomically in the private operator SQLite. Source calls have no receipt UNION, global grouping, joins, counts, or cache-value audit scans. Text byte limits are checked inside source SQLite before RPC construction: thread/Discord/interaction IDs 20 bytes, title fields and keys 4096 bytes, digests 64 bytes. Overlong text becomes a diagnostic flag; it is never silently treated as absent. Numeric validity uses the same safe-integer/text schemas as final export. Complete all seven tables, including empty terminal pages; missing pages block audit/export. Then run `auditNext()` until complete, one local indexed page per RPC. Counts, duplicate ownership and completeness accumulate in the private SQLite; `inventory(after)` and `auditPage(after)` read that immutable audit, never the old Hub. No arbitrary cache values leave the source.
2. Collect every page to `complete=true`, not only recently active conversations. Include post-less conversations and orphan jobs/guards in the audit even though only known threads are staged for adoption. A missing main row does not prove a job/send absent. Unsupported schemas, unknown authoritative keys, orphan/unknown posts, or unaccounted send effects stop the cut. Use the old relay's authoritative mapping inventory to repair missing `relay.linkAttribute` values only in configured relayed inboxes. Do not create links or threads in excluded archive inboxes. Already linked historical threads still require authoritative receipt accounting; an excluded or attribute-only record must be explicitly reconciled, never silently omitted. Also enumerate Chatwoot conversations with that custom attribute (all statuses/pages, or its official conversation filter), so an attribute-only post is not omitted from the manifest. Resolve conflicts rather than overwriting them. A missing attribute alone never proves there was no post.
3. `verifyLinks(cut, chatwoot, rest, attribute, settings)` fresh-reads each conversation, verifies its real Discord guild/forum, repairs only a missing link within configured relayed inboxes and fresh-confirms the exact URL. A conflicting URL, excluded inbox repair, missing conversation, 403 or unavailable read fails. Repeat this check after draining. Freeze the verified mapping manifest for the cut epoch; adoption rechecks the same link before it deletes anything. No runtime old-Hub fallback exists.
4. Verify `VIEW_CHANNEL`, `READ_MESSAGE_HISTORY`, `MANAGE_MESSAGES`, and visibility of our historical standalone V2 card components in every thread. An empty history response without these permissions is not absence proof. Record all actual legacy webhook ids per forum, including rotations. Names/avatars are not ownership. Prewarm `ForumRegistry.lookup(forum)` until ready before activation; only its alarm discovers/creates webhooks.
5. Any archived routing guard blocks this operator, including a cut labelled `independent-router`. There is no executable independently-owned-router evidence path here; do not relabel nonzero guards `never-used`, erase them or delete the Hub with its only `kind-reply` guard. Return that handover need for separate review. The receipt export includes every `submitted_responses` digest. The terminal cache scan page captures only the canonical numeric `queue:escalations` baseline (bounded to 1 MiB), even when absent (`{}`), and its hash binds it to the frozen checkpoint. `operator.escalationBaseline(source)` returns the durably collected value; the cut must equal it. Changed replay or a stale `{}` fails. Every source response and collector input is also bounded to 2 MiB of encoded UTF-8. No other cache values leave the source.

## The quiesced cut

1. Pause new human admission and every source that can create eligible messages: external inbound sources, bot actions, Chatwoot/Sidekiq activity jobs and queued channel deliveries. New commands must receive the maintenance refusal immediately: **not accepted or executed**. Continue accepting signed webhook events durably in the maintenance targets; no target alarm executes them yet. A timed-out normal admission is different: it may have committed and must say its acceptance is unconfirmed.
2. Drain the old relay to complete message boundaries. `jobs=0` is necessary and insufficient, especially for 0.27 which removed command jobs before executing them. Obtain explicit evidence that all old requests/alarms and upstream asynchronous creation work have settled, including requests accepted without a response. No in-flight write, held pending body, partial message plan, backlog or unexplained UNKNOWN may be converted into READY. Do not release pending bodies early to force a watermark. If A100 is unfinished while B101 was sent, a common W=101 is invalid. If sources cannot be genuinely quiesced, stop this preservation cut and return the need for a separate handover decision.
3. At that quiesced moment record W, not a wall-clock-derived snowflake or a guessed newest page id. For every conversation verify its processed cursor covers its latest eligible message and no eligible id exceeds W. W must cover the actually committed, drained sources; sequence gaps and delayed activity/import transactions prevent inferring it from one latest conversation. The cut's numeric interaction fence I must exactly equal the archive's retained maximum (BigInt, never lexical ordering). Stock 0.27 prunes these rows after an hour: independent admission evidence must show this retained maximum is sufficient. If it is insufficient or unavailable, this operator cannot accept a guessed/substituted fence; stop for separately reviewed evidence handover. An old open editor must be reopened in the new epoch.
4. Wait until all known old Discord/Chatwoot cooldowns expire. Do not reset a live 429 cooldown by changing namespaces. Start triage and digest at the **next UTC hour**, configured with `notificationsAfter`, so the cut hour cannot receive a second quota/digest. Preserve the authoritative exported escalation baseline, including an explicitly absent source baseline (`{}`). An unavailable or invalid baseline blocks staging; do not infer the old coordination state from fresh wait states.
5. Stop the old cron/ingress executor and verify it cannot start another write. The new build retains a retired Hub shell: old alarms only delete their alarm; no job forwarding or business execution. Code updates are eventually consistent and `deleteAlarm` does not cancel an in-flight HTTP request. Wait for explicit old-executor retirement evidence; switching the webhook URL is not a sender fence.

## Stage, activate and observe

Construct the strict `AdoptionCut` from the verified inventory and drain evidence. `validateCut` refuses incomplete inventories, ambiguous work, duplicate owners, live cooldowns and cursor gaps. Keep its private evidence alongside the backup. The code deliberately cannot certify the external pause/drain merely from an operator-supplied zero.

Collect the whole frozen source before building the cut:

```ts
let checkpoint = await operator.open(source); // immutable deployed boundary
while (!checkpoint.complete) {
  checkpoint = await operator.collect(source, checkpoint.next); // persists before reply
}
// Read every baselinePage(after) into a private worksheet BEFORE auditing.
// It returns exact source owner/message/digest plus recorded/unresolved linkage, at most 100 rows.
// Review authoritative evidence and supply deleted-source dispositions here.
// Unexplained/pre-migration existing posts remain unresolved; never infer Discord IDs.
while (!(await operator.auditNext()).complete) {}
```

Save the durable operator archive/receipts and privately collect every `inventory`/`auditPage` page. Diagnostics identify table kind, rowid and owner; unsupported cache keys and invalid text are not logged. Replay the complete source scan with the same boundary/checkpoints and compare stored page digests before committing the cut. Caller timeout means unconfirmed collection, not cancellation; retry the identical checkpoint only after the source invocation settles. Frozen source mutation/change requires a new epoch/archive and a new complete audit.

Nonzero `orphaned`, `conflicting`, `invalid`, `unsupported` or `unresolved` blocks the cut. Normal 0.27 deletion removes derived IDs but deliberately retains the response digest. Migration 8 also added derived/title associations without backfill. A baseline-only row is therefore **unresolved provenance**, not universally corruption. For an authoritative deleted Chatwoot source, retain the immutable private deletion record and use `operator.disposition(source,accountId,conversationId,messageId,digest,evidenceRef)` before auditing. The executable disposition requires the exact frozen owner/message/digest, refuses an existing derived ID or conflicting evidence, and is exported in the response record and final hash. Target import stores it transactionally alongside the unchanged digest. The evidence must explain completed legacy receipt deletion, rather than merely showing a current Chatwoot deleted flag: that flag cannot prove an unrecorded/crash Discord post is gone. The evidence reference must identify immutable authoritative deletion evidence reviewed by the operator; the code cannot authenticate an external deletion record from its name. Never delete the baseline to clear the audit.

An `evidenceRef` is a reviewed artifact locator, not recovered history. Accept it only with an immutable pre-loss receipt/deletion ledger identifying the exact owner/message/digest and Discord send/delete outcome. Stock 0.27's deletion log lacks the Discord ID; current Chatwoot deletion flags, Discord absence, ordinary relay logs and settlement evidence alone are insufficient. Without that external artifact, preserve the baseline in `baselinePage`/the archive as unresolved and keep the cut blocked. No local test establishes that this installation possesses such evidence.

A still-existing pre-migration post with no recorded Discord ID, or an unexplained crash between baseline and derived writes, remains unresolved and blocks this cut. An exact authoritative receipt backup may support separately reviewed repair; content/time/history similarity cannot. This protocol does not restore information the old system never recorded. A recorded title with NULL `title_message_id` is preserved as `never-recorded-or-unresolved`: contact renames still retain its subject, and deletion cannot clear that subject by guessing an association. A non-null title ID with a nonempty subject still requires its exact posted receipt; the old normal deletion may already have cleared the subject while retaining its ID. Missing recorded data is a different failure from preexisting unsupported linkage.

Audit unthreaded conversations too; `auditedUnthreaded` requires no receipts/title/unknown sends. Enumerate Chatwoot links across all statuses and reconcile against source mappings. The initial live read-only inventory (157 conversations, 53 linked) is a starting observation, not post-drain coverage. All 104 unlinked records were in excluded archives 13/14; create no archive links/threads. Freshly repeat/reconcile these counts at the cut. Attribute-only/source-only/conflicting records cannot be omitted.
For **each** source thread, collect a separate receipt stream. Do not put all a large ticket's receipts into an inventory row or cut manifest:

```ts
// Private trusted RPC client; save each returned page to a private artifact before advancing.
let page = await operator.receiptPage(accountId, conversationId);
await validateReceiptPage(page);
await savePrivatePage(page); // operator-owned storage, no console output
while (!page.complete) {
  page = await operator.receiptPage(accountId, conversationId, nextReceiptPosition(page));
  await validateReceiptPage(page);
  await savePrivatePage(page);
}
const history = await operator.receiptSeal(accountId, conversationId); // canonical completed archive chain
```

The first hash covers the source Hub object id (`sourceIdentity`), schema, owner/thread, source cursor, nullable `title_subject`, `title` and `title_message_id`, explicit title association provenance, and all three table counts. Each ordered page extends SHA-256 over its predecessor, cursor, records and completion flag. Compare the final per-conversation seals against the privately retained source scan; the frozen shell does not certify prior unsettled external writers. Never resume or edit a stream after source changes. The cut's `sourceIdentity` must equal every header's actual Hub object id from the private RPC (not a chosen label). That identity, backup reference and `drainEvidence` must identify the actual old namespace and frozen boundary. The digest checks artifact integrity/completeness, not external deployment authority or proof of source quiescence.

The private operator checks `assertCut` before prepare/verify/stage: the cut epoch, source id, schema, drain evidence, all table counts and complete expected owner/thread/cursor set must equal its frozen archive. Each mapping's full seal must equal the durably generated canonical page chain (page count, final digest and final position); changing a Discord ID/baseline while retaining its header/counts cannot pass. Each `receiptPage` call advances at most 100 actual rows, atomically stores the page/checkpoint, and only accepts the next checkpoint or an identical replay. Owner counts accumulate during audit; page generation never recounts an entire ticket. Missing pages cannot produce a canonical seal. Jobs/partial counts and interaction fence must match the archive; any job, partial work, unknown card/guard or routing guard blocks even a zero-mapping cut. The escalation baseline must equal the frozen cache checkpoint. A re-counted subset cut cannot bypass these gates. Construct the complete strict cut: each mapping has `history` instead of an unbounded response array; copy `sourceCounts` and zero `receiptAudit` from the final inventory and include `auditedUnthreaded`. `validateCut` requires every source thread and all posted/derived/response totals to be accounted for, unique ownership, matching header/schema/cursor, and a cursor not beyond W. A linked conversation missing its source row/receipts is a blocker requiring evidence-based repair. An empty stream is valid only when the authoritative source itself reports all counts zero; never use it to replace unknown history. Old partial deletions can leave gaps in part numbers; preserve the actual rows, do not fill gaps or infer an absent part.

After the old executor is verifiably retired, configure the target's `cutover.phase=maintenance`, the same epoch, `interactionFence=I`, `relay.startAfterMessageId=W`, `notificationsAfter` and `legacyWebhooks`. This CONFIG must be deployed to the actual Conversation DOs, not just to the operator. Perform these private RPC steps:

1. `prepare(cut)` validates the entire cut/config before mutations, claims every Directory owner/generation and persists immutable per-conversation history seals. It imports no live effects.
2. `importPage(page)` sends the saved pages in order, **one page per RPC**. Each page's receipts, observed response revisions, digest and checkpoint commit atomically. Retry the identical page after a crash or timeout; changed replay, duplicate Discord ids/natural keys, mismatched source or over-count fails closed.
3. `seal(accountId, conversationId)` checks final digest, page count, all table counts and actual target row counts. It requires the same maintenance epoch and Directory generation. Missing pages never count as complete.
4. Fresh-verify the **complete** cut after drain with `verify(cut,batch)`, for every zero-based batch in `0..Math.ceil(cut.mappings.length/2)-1`. Pass the same full cut each time; never construct subset cuts. With 53 mappings this is 27 calls. Each call checks at most two mappings and persists a coverage receipt tied by SHA-256 to the whole strict cut, including epoch, source, drain evidence and every expected mapping/seal. Failure/timeout creates no successful coverage. Receipts survive restart; changing any cut field requires fresh coverage. Missing-link repairs stay within configured inboxes, and excluded archives are never repaired. Retain all receipts and perform fresh post-drain reads; initial observation is insufficient.
5. `stage(cut)` checks all verification batches and requires **every** mapping to have sealed history before it marks any ready for activation and stages the digest baseline. Rerun an identical cut after a lost receipt. Obtain all successful receipts; do not activate after any failed claim/import/seal/stage.

Maintenance admits events durably without executing them. A staged but incomplete history also fences execution if someone removes cutover CONFIG or prematurely switches to active. No cleanup or command effects escape that fence. New owners never query the source Hub during online execution.

Set the same cut to active only after every precondition and stage receipt is verified. Request `AccountSweep.request(account,true)` and enqueue every staged conversation (including silent/window-excluded targets) for the first reconcile. Restore sources after the new sole owner is active. Keep the old shell and private evidence during the observation window.

On first use the Conversation rechecks its link and real guild/forum, claims the Directory and runs recoverable history cleanup before making a fresh card. Cleanup pages `limit=100` with persisted `before`/pending deletes. It deletes only an empty-body standalone V2 ticket card of a verified old webhook with the exact ticket-card shape. It never deletes ordinary mirror bodies, even when they have buttons, or another webhook's messages. Individual DELETE accepts a real 404 and retries other failures; it uses no two-week bulk-delete shortcut. Cleanup-complete persists before new card creation. In the final adoption transaction, the target installs W and restores all three nullable title fields without clearing imported receipt tables. Imported pre-W messages are deleted through the bot/channel single-message endpoint, so webhook rotation cannot turn a wrong-webhook 404 into false absence; only confirmed deletion or specific Unknown Message/Channel 404 clears a receipt, and 403/network errors retain it. This requires the verified `MANAGE_MESSAGES` permission ([Discord contract](https://docs.discord.com/developers/resources/message#delete-message)). An UNKNOWN new card stays unaddressable and is never automatically created again; other metadata, mirrors and human commands continue. Register a real resource id only through explicit repair after investigating Discord.

## Preserved history and other boundaries

- Drafts are not imported. A missing/stale draft gives the explicit **Apps → Reply with this** fallback; new cards omit it. Old modal submissions and late answers cannot restore a draft without a current source/generation.
- Hourly counters reset at the next UTC hour. Notifications do not restart the old hour's quota. Digest/escalation baselines have separate handling above.
- Pre-W original/derived receipts and nullable title association/metadata must be imported completely. Deleting their Chatwoot source removes only their authoritative Discord ids; deleting a recorded title source drops its subject, and contact-name changes continue to update retained titles. A historically NULL association stays NULL with explicit provenance; no delete linkage is invented. Legacy rows whose title was never recorded keep that behavior. This path does not accept historical deletion/title data loss.
- Completeness covers records the source actually owns. A legacy write that succeeded remotely but never recorded a receipt cannot be recovered from similarity or inferred as unsent; unexplained outcomes and unsupported/orphan/conflicting records block the cut. Preserve customer history while obtaining separately reviewed authoritative evidence or repair. Local fixtures never prove real data was repaired.
- Old CSAT/delivery updates are **not frozen**: minimal observed digests are staged, unchanged old updates do not repost, and a genuinely changed old response can still publish. Its newly created receipt supports subsequent deletion. Pending hold semantics are unchanged.
- Old command results cannot be declared uniformly unexecuted merely by dropping their rows. Unexplained prior write outcomes block this cut. New message creation UNKNOWN remains UNKNOWN without history matching or resend.

## Rollback and Hub deletion

Before **any** target business effect or old-card DELETE, an abort can stop new admission/alarms, account for all durably accepted maintenance events/commands, and restore the fully quiesced old executor with those events explicitly handled. Never ACK and silently discard them.

After new DOs have posted or changed Chatwoot, restoring an old snapshot is not clean rollback. Old cursor 100 would repost new 101/102; deleted old cards cannot be restored from SQLite; Chatwoot mutations cannot be undone by restoring DO storage; new durable alarms must be retired before another owner runs. Prefer forward repair in these namespaces. Returning to a Hub requires another stop/drain and explicit checkpoint/effect handover or a newly authorized historical cut and losses. Cloudflare version rollback cannot cross a class-lifecycle change.

After the separately authorized observation window, verify all old routing guards/evidence are accounted for and all old references are gone. `cloudflare.config.ts` mode `retire-hub` uses `src/active.ts` without a Hub export and declares **only Hub** `exports.durableObject({state:"deleted"})`; every partition class remains SQLite. Review its built/prebuilt dry-run lifecycle plan before any authorized deployment. The permanent delete is irreversible; do not claim PITR revives a deleted namespace. Subsequent source cleanup removes the retired shell/inventory control and completed cutover tooling in a separate reviewed change; permanent online effect guards, generation and source boundaries remain.

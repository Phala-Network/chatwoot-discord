# Conversation ownership cutover and rollback

This is a maintenance operation requiring the owner's separate deployment authorization. Do not run it as an ordinary version update. The namespace names are stable: `conversation:v1:<account>:<conversation>`, `thread:v1:<thread>`, `account:v1:<account>`, `forum:v1:<forum>`, and `digest:v1:<channel>`. Each installation has independent namespaces. Never point a second installation at these namespaces.

## Inventory while the old relay can still explain its posts

1. Verify the actual Worker/Hub namespace identity and SQLite schema (live 0.27/0.29 schema 9; this branch schema 10). Keep a private backup for the observation window. `legacyInventory` in `src/legacy.ts` is read-only; it pages the entire `conversations` table, including silent/resolved posts, and exposes ids, cursors, counts and response digests, never cache values, message bodies or credentials. The retired `Hub.inventory(after)` is the same trusted-binding RPC. It has no public HTTP route. A temporary, authenticated operator binding may call it; do not add that binding to online ingress. Do not log its full private manifest.
2. Collect every page to `complete=true`, not only recently active conversations. Include post-less conversations and orphan jobs/guards in the audit even though only known threads are staged for adoption. A missing main row does not prove a job/send absent. Unsupported schemas, unknown authoritative keys, orphan/unknown posts, or unaccounted send effects stop the cut. Use the old relay's mapping inventory to repair missing `relay.linkAttribute` values. Also enumerate Chatwoot conversations with that custom attribute (all statuses/pages, or its official conversation filter), so an attribute-only post is not omitted from the manifest. Resolve conflicts rather than overwriting them. A missing attribute alone never proves there was no post.
3. `verifyLinks(cut, chatwoot, rest, attribute)` fresh-reads each conversation, verifies its real Discord guild/forum, repairs only a missing link and fresh-confirms the exact URL. A conflicting URL, missing conversation, 403 or unavailable read fails. Repeat this check after draining. Freeze the verified mapping manifest for the cut epoch; adoption rechecks the same link before it deletes anything. No runtime old-Hub fallback exists.
4. Verify `VIEW_CHANNEL`, `READ_MESSAGE_HISTORY`, `MANAGE_MESSAGES`, and visibility of our historical standalone V2 card components in every thread. An empty history response without these permissions is not absence proof. Record all actual legacy webhook ids per forum, including rotations. Names/avatars are not ownership. Prewarm `ForumRegistry.lookup(forum)` until ready before activation; only its alarm discovers/creates webhooks.
5. Resolve the old routing guards: prove an independent Router owns them, or prove routing was never used. Do not delete the Hub with its only `kind-reply` guard. Export the minimal `submitted_responses` digests by conversation and `queue:escalations` watermark. These preserve old CSAT/delivery change behavior and prevent a repeated escalation; they are not draft/counter migration.

## The quiesced cut

1. Pause new human admission and every source that can create eligible messages: external inbound sources, bot actions, Chatwoot/Sidekiq activity jobs and queued channel deliveries. New commands must receive the maintenance refusal immediately: **not accepted or executed**. Continue accepting signed webhook events durably in the maintenance targets; no target alarm executes them yet. A timed-out normal admission is different: it may have committed and must say its acceptance is unconfirmed.
2. Drain the old relay to complete message boundaries. `jobs=0` is necessary and insufficient, especially for 0.27 which removed command jobs before executing them. Obtain explicit evidence that all old requests/alarms and upstream asynchronous creation work have settled, including requests accepted without a response. No in-flight write, held pending body, partial message plan, backlog or unexplained UNKNOWN may be converted into READY. Do not release pending bodies early to force a watermark. If A100 is unfinished while B101 was sent, a common W=101 is invalid. If sources cannot be genuinely quiesced, stop this zero-checkpoint cut and return the need for a separate handover decision.
3. At that quiesced moment record W, not a wall-clock-derived snowflake or a guessed newest page id. For every conversation verify its processed cursor covers its latest eligible message and no eligible id exceeds W. W must cover the actually committed, drained sources; sequence gaps and delayed activity/import transactions prevent inferring it from one latest conversation. Record the old numeric maximum accepted interaction id I after old admission is stopped (BigInt, never lexical ordering). An old open editor must be reopened in the new epoch.
4. Wait until all known old Discord/Chatwoot cooldowns expire. Do not reset a live 429 cooldown by changing namespaces. Start triage and digest at the **next UTC hour**, configured with `notificationsAfter`, so the cut hour cannot receive a second quota/digest. Preserve the exported escalation baseline; if unavailable, derive a conservative baseline from fresh wait states and document the suppressed current escalation before proceeding.
5. Stop the old cron/ingress executor and verify it cannot start another write. The new build retains a retired Hub shell: old alarms only delete their alarm; no job forwarding or business execution. Code updates are eventually consistent and `deleteAlarm` does not cancel an in-flight HTTP request. Wait for explicit old-executor retirement evidence; switching the webhook URL is not a sender fence.

## Stage, activate and observe

Construct the strict `AdoptionCut` from the verified inventory and drain evidence. `validateCut` refuses incomplete inventories, ambiguous work, duplicate owners, live cooldowns and cursor gaps. Keep its private evidence alongside the backup. The code deliberately cannot certify the external pause/drain merely from an operator-supplied zero.

Configure `cutover.phase=maintenance`, the same epoch, `interactionFence=I`, `relay.startAfterMessageId=W`, `notificationsAfter` and `legacyWebhooks`. Call `stageAdoption` through the private trusted operator binding. It checks that configuration matches the sealed cut, stages the digest baseline, prebuilds **every** legacy ThreadDirectory owner and stages each Conversation with its response baselines. Calls are bounded and idempotent: after a lost receipt rerun the same manifest, never a different epoch. Keep maintenance until every target receipt has been obtained; any failed claim/stage blocks activation. This makes commands on silent old threads routable before first new Chatwoot activity. Do not use the online Worker as a public importer.

Set the same cut to active only after every precondition and stage receipt is verified. Request `AccountSweep.request(account,true)` and enqueue every staged conversation (including silent/window-excluded targets) for the first reconcile. Restore sources after the new sole owner is active. Keep the old shell and private evidence during the observation window.

On first use the Conversation rechecks its link and real guild/forum, claims the Directory and runs recoverable history cleanup before making a fresh card. Cleanup pages `limit=100` with persisted `before`/pending deletes. It deletes only an empty-body standalone V2 ticket card of a verified old webhook with the exact ticket-card shape. It never deletes ordinary mirror bodies, even when they have buttons, or another webhook's messages. Individual DELETE accepts a real 404 and retries other failures; it uses no two-week bulk-delete shortcut. Cleanup-complete persists before new card creation. An UNKNOWN new card stays unaddressable and is never automatically created again; other metadata, mirrors and human commands continue. Register a real resource id only through explicit repair after investigating Discord.

## Accepted losses and preserved boundaries

- Drafts are not imported. A missing/stale draft gives the explicit **Apps → Reply with this** fallback; new cards omit it. Old modal submissions and late answers cannot restore a draft without a current source/generation.
- Hourly counters reset at the next UTC hour. Notifications do not restart the old hour's quota. Digest/escalation baselines have separate handling above.
- Deletion sync for pre-W messages is lost: their old Discord receipt/title associations are not imported. Deleting such a Chatwoot message does not remove its old Discord mirror; handle that history manually when required.
- Old CSAT/delivery updates are **not frozen**: minimal observed digests are staged, unchanged old updates do not repost, and a genuinely changed old response can still publish. Its newly created receipt supports subsequent deletion. Pending hold semantics are unchanged.
- Old command results cannot be declared uniformly unexecuted merely by dropping their rows. Unexplained prior write outcomes block this cut. New message creation UNKNOWN remains UNKNOWN without history matching or resend.

## Rollback and Hub deletion

Before **any** target business effect or old-card DELETE, an abort can stop new admission/alarms, account for all durably accepted maintenance events/commands, and restore the fully quiesced old executor with those events explicitly handled. Never ACK and silently discard them.

After new DOs have posted or changed Chatwoot, restoring an old snapshot is not clean rollback. Old cursor 100 would repost new 101/102; deleted old cards cannot be restored from SQLite; Chatwoot mutations cannot be undone by restoring DO storage; new durable alarms must be retired before another owner runs. Prefer forward repair in these namespaces. Returning to a Hub requires another stop/drain and explicit checkpoint/effect handover or a newly authorized historical cut and losses. Cloudflare version rollback cannot cross a class-lifecycle change.

After the separately authorized observation window, verify all old routing guards/evidence are accounted for and all old references are gone. `cloudflare.config.ts` mode `retire-hub` uses `src/active.ts` without a Hub export and declares **only Hub** `exports.durableObject({state:"deleted"})`; every partition class remains SQLite. Review its built/prebuilt dry-run lifecycle plan before any authorized deployment. The permanent delete is irreversible; do not claim PITR revives a deleted namespace. Subsequent source cleanup removes the retired shell/inventory control and completed cutover tooling in a separate reviewed change; permanent online effect guards, generation and source boundaries remain.

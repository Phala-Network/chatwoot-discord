# Conversation ownership cutover and rollback

This is a maintenance operation requiring the owner's separate deployment authorization. Do not run it as an ordinary version update. The namespace names are stable: `conversation:v1:<account>:<conversation>`, `thread:v1:<thread>`, `account:v1:<account>`, `forum:v1:<forum>`, and `digest:v1:<channel>`. Each installation has independent namespaces. Never point a second installation at these namespaces.

## Private operator artifact

Use an operator artifact built from the **reviewed preservation change**, not the already published 0.31.0 operator (which lacks receipt handover). Its emitted `chatwoot-discord-relay/operator` module exports `inventory`, `receiptPage`, `auditPage`, `keyPage`, `escalationBaseline`, `nextReceiptPosition`, `receiptSeal`, `validateReceiptPage`, `verifyAdoptionLinks`, `verifyLinks`, `validateCut`, `cutSchema`, `prepareAdoption`, `importAdoptionPage`, `sealAdoptionHistory` and `stageAdoption`. No new version is implied by this runbook.

The package includes [operator.ts](operator.ts) and [operator.config.ts](operator.config.ts), a private Durable Object RPC service and binding template. Copy them into a separately reviewed operator project, rename the configuration to `cloudflare.config.ts`, and use its standard Cloudflare Vite setup. Replace every placeholder identity and CONFIG from the sealed installation configuration. `LEGACY_HUB` references the original source namespace and object `global`; the partition bindings reference the target relay namespaces. Before old-executor retirement, that source must run the separately reviewed bridge below. After retirement it may run the retained shell. Neither a fresh Hub nor a namespace copy is a source.

Bind a trusted private client with `bindings.durableObject({worker:"relay-adoption-operator",exportName:"RelayAdoptionOperator"})`. Disable routes, workers.dev and preview URLs; the template's HTTP handler always returns 404. Never bind it to online ingress. The private service exposes `inventory`, `receiptPage`, `auditPage`, `keyPage`, `escalationBaseline`, `verify`, `prepare`, `importPage`, `seal` and `stage`. Source reads have a ten-second private deadline; online control deadlines are unchanged. Discord checks use the normal scoped limiter and durable cooldown reports.

Keep backups, titles, receipt pages and manifests in access-controlled **private artifacts**, never application logs, shell tracing, tickets or public build output. Titles can contain customer text even though receipt pages contain no message bodies, cached credentials or webhook tokens. Operator errors deliberately omit page/header values. Preserve an identical artifact when retrying a lost RPC receipt. Remove the private operator after separately authorized close-out.

## Actual live 0.27 source access

**Stock 0.27.0 has no inventory/export RPC.** A private binding cannot read another DO's SQLite, and deploying the new retained shell first would retire the old executor before source drain evidence exists. The minimum supported source path is [legacy-source-bridge.ts](legacy-source-bridge.ts): it subclasses the exact old `Hub`, adds only bounded read methods and reuses the old default Worker handler. Its inherited enqueues, drafts, routing guards, queue, alarm and schema9 Store remain the old implementation. It never instantiates the new Store or migrates source SQLite.

In a separately reviewed source deployment project, install `legacy-relay` as `npm:chatwoot-discord-relay@0.27.0` (verify the tarball against the actual deployed source/version), install the reviewed preservation artifact under its normal package name, and copy the bridge as the entrypoint. Retain and verify the actually deployed old dependency graph/lock and build settings; the alias fixture proves API compatibility, not binary equivalence to production. If that graph cannot be reproduced, review a source-only patch adding these read methods to the original pinned Hub instead of rebuilding the executor with newly resolved dependencies. Keep the original Worker name, original Hub lifecycle/namespace, HUB binding, CONFIG, secrets and cron configuration; do not add partition classes or change handlers in that bridge deployment. Build and inspect a dry-run plan. Package checks compile this bridge against the actual 0.27.0 package; they do not certify any installation's deployed identity or retirement.

This bridge requires **separate maintenance deployment authorization and review**. No existing live export access is assumed. Before authorizing it, retain available old ingress/request/routing evidence and a private backup. Stock 0.27 has no new `cutover.phase` admission gate. Do not pass the new cutover CONFIG into its strict old parser. Establish a separately reviewed external maintenance refusal/admission boundary, pause upstream creation/delivery work, and stop new old-cron sweep/queue admission while retaining old alarms long enough to drain. A switched URL, disabled alarm or empty job count alone does not establish that boundary. After the bridge is installed, use only a private trusted binding for preliminary source reads. Preliminary reads while the executor is running are not a sealed cut. Pause admission/upstream sources, drain the inherited old executor, certify settled requests/alarms (0.27 removes command jobs before execution), then freeze and collect the final export **before** old-executor retirement. Collect source guards and counts at that boundary; replacing a Worker version does not cancel an in-flight request.

If a different source version or patched implementation is actually deployed, or the old request evidence cannot establish a settled boundary, stop for review. A missing/ambiguous authoritative record blocks the preservation cut. Do not fabricate it from Discord content, timestamps, history similarity, Chatwoot links or a guessed watermark.

## Inventory while the old relay can still explain its posts

1. Verify the actual Worker/Hub namespace identity and SQLite schema (live 0.27/0.29 schema 9; this branch schema 10). Keep a private backup for the observation window. `legacyInventory` in `src/legacy.ts` is read-only; it pages the entire `conversations` table, including silent/resolved posts, and exposes ids, cursors, counts and audit totals. Receipts and private title metadata are exported separately per conversation, at most 100 records per page. The bridge and retired `Hub` provide the same private read RPCs. It has no public HTTP route. A temporary, authenticated operator binding may call it; do not add that binding to online ingress. Do not log its full private manifest.
2. Collect every page to `complete=true`, not only recently active conversations. Include post-less conversations and orphan jobs/guards in the audit even though only known threads are staged for adoption. A missing main row does not prove a job/send absent. Unsupported schemas, unknown authoritative keys, orphan/unknown posts, or unaccounted send effects stop the cut. Use the old relay's authoritative mapping inventory to repair missing `relay.linkAttribute` values only in configured relayed inboxes. Do not create links or threads in excluded archive inboxes. Already linked historical threads still require authoritative receipt accounting; an excluded or attribute-only record must be explicitly reconciled, never silently omitted. Also enumerate Chatwoot conversations with that custom attribute (all statuses/pages, or its official conversation filter), so an attribute-only post is not omitted from the manifest. Resolve conflicts rather than overwriting them. A missing attribute alone never proves there was no post.
3. `verifyLinks(cut, chatwoot, rest, attribute, settings)` fresh-reads each conversation, verifies its real Discord guild/forum, repairs only a missing link within configured relayed inboxes and fresh-confirms the exact URL. A conflicting URL, excluded inbox repair, missing conversation, 403 or unavailable read fails. Repeat this check after draining. Freeze the verified mapping manifest for the cut epoch; adoption rechecks the same link before it deletes anything. No runtime old-Hub fallback exists.
4. Verify `VIEW_CHANNEL`, `READ_MESSAGE_HISTORY`, `MANAGE_MESSAGES`, and visibility of our historical standalone V2 card components in every thread. An empty history response without these permissions is not absence proof. Record all actual legacy webhook ids per forum, including rotations. Names/avatars are not ownership. Prewarm `ForumRegistry.lookup(forum)` until ready before activation; only its alarm discovers/creates webhooks.
5. Resolve the old routing guards: prove an independent Router owns them, or prove routing was never used. Do not delete the Hub with its only `kind-reply` guard. The receipt export includes every `submitted_responses` digest. `escalationBaseline()` exports only the named numeric `queue:escalations` baseline (bounded to 1 MiB), never arbitrary cache values. Save and repeat it at the frozen source boundary; use it as the cut's `escalationBaseline`. Missing source access blocks this cut. These preserve old CSAT/delivery change behavior and prevent a repeated escalation; they are not draft/counter migration.

## The quiesced cut

1. Pause new human admission and every source that can create eligible messages: external inbound sources, bot actions, Chatwoot/Sidekiq activity jobs and queued channel deliveries. New commands must receive the maintenance refusal immediately: **not accepted or executed**. Continue accepting signed webhook events durably in the maintenance targets; no target alarm executes them yet. A timed-out normal admission is different: it may have committed and must say its acceptance is unconfirmed.
2. Drain the old relay to complete message boundaries. `jobs=0` is necessary and insufficient, especially for 0.27 which removed command jobs before executing them. Obtain explicit evidence that all old requests/alarms and upstream asynchronous creation work have settled, including requests accepted without a response. No in-flight write, held pending body, partial message plan, backlog or unexplained UNKNOWN may be converted into READY. Do not release pending bodies early to force a watermark. If A100 is unfinished while B101 was sent, a common W=101 is invalid. If sources cannot be genuinely quiesced, stop this preservation cut and return the need for a separate handover decision.
3. At that quiesced moment record W, not a wall-clock-derived snowflake or a guessed newest page id. For every conversation verify its processed cursor covers its latest eligible message and no eligible id exceeds W. W must cover the actually committed, drained sources; sequence gaps and delayed activity/import transactions prevent inferring it from one latest conversation. Record the old numeric maximum accepted interaction id I after old admission is stopped (BigInt, never lexical ordering). Inventory reports only retained interaction rows; 0.27 prunes them after an hour, so use prior admission evidence when that retained maximum is insufficient. Do not guess I from time. An old open editor must be reopened in the new epoch.
4. Wait until all known old Discord/Chatwoot cooldowns expire. Do not reset a live 429 cooldown by changing namespaces. Start triage and digest at the **next UTC hour**, configured with `notificationsAfter`, so the cut hour cannot receive a second quota/digest. Preserve the authoritative exported escalation baseline, including an explicitly absent source baseline (`{}`). An unavailable or invalid baseline blocks staging; do not infer the old coordination state from fresh wait states.
5. Stop the old cron/ingress executor and verify it cannot start another write. The new build retains a retired Hub shell: old alarms only delete their alarm; no job forwarding or business execution. Code updates are eventually consistent and `deleteAlarm` does not cancel an in-flight HTTP request. Wait for explicit old-executor retirement evidence; switching the webhook URL is not a sender fence.

## Stage, activate and observe

Construct the strict `AdoptionCut` from the verified inventory and drain evidence. `validateCut` refuses incomplete inventories, ambiguous work, duplicate owners, live cooldowns and cursor gaps. Keep its private evidence alongside the backup. The code deliberately cannot certify the external pause/drain merely from an operator-supplied zero.

While the source is frozen and before retirement, collect every `inventory(after)` page to `complete=true`, checking that its schema, global counts, interaction fence and audit totals remain identical. Paginate `auditPage` for offending receipt ids and `keyPage` for cache key disposition (neither returns secret values). Nonzero `orphaned`, `conflicting`, `invalid` or `unsupported` blocks the cut. Unknown receipt columns/schema/tables are rejected. A nonempty recorded title without its authoritative source association/receipt, a response baseline without any derived receipt, or a derived receipt without its response baseline is reported as invalid and blocks the cut. An unpaired record may be a legitimately deleted source, an unrecorded write or a lost baseline; none is inferred. Preserve the baseline/private evidence and obtain a separately reviewed disposition from authoritative source/deletion records before recollecting a clean cut. Never drop a baseline simply to clear this audit. Audit all source rows, including unthreaded conversations; they can count as `auditedUnthreaded` only after proving they own no receipts/title association and no unexplained jobs or sends. Enumerate Chatwoot links separately across all statuses, reconcile them against source mappings, and account for excluded inboxes without creating archive links or threads.

For **each** source thread, collect a separate receipt stream. Do not put all a large ticket's receipts into an inventory row or cut manifest:

```ts
// Private trusted RPC client; save each returned page to a private artifact before advancing.
let page = await operator.receiptPage(accountId, conversationId);
await validateReceiptPage(page);
await savePrivatePage(page); // operator-owned storage, no console output
while (!page.complete) {
  page = await operator.receiptPage(accountId, conversationId, nextReceiptPosition(page));
  await validateReceiptPage(page);
  await savePrivatePage(page);
}
const history = receiptSeal(page); // put only this header/count/digest seal in the mapping
```

The first hash covers the source Hub object id (`sourceIdentity`), schema, owner/thread, source cursor, nullable `title_subject`, `title` and `title_message_id`, and all three table counts. Each ordered page extends SHA-256 over its predecessor, cursor, records and completion flag. Replay the **whole** frozen export once more and compare page digests and final seals before retirement; source reads alone cannot fence a concurrent writer. Never resume or edit a stream after source changes. The cut's `sourceIdentity` must equal every header's actual Hub object id from the private RPC (not a chosen label). That identity, backup reference and `drainEvidence` must identify the actual old namespace and frozen boundary. The digest checks artifact integrity/completeness, not external deployment authority or proof of source quiescence.

Construct the complete strict cut: each mapping has `history` instead of an unbounded response array; copy `sourceCounts` and zero `receiptAudit` from the final inventory and include `auditedUnthreaded`. `validateCut` requires every source thread and all posted/derived/response totals to be accounted for, unique ownership, matching header/schema/cursor, and a cursor not beyond W. A linked conversation missing its source row/receipts is a blocker requiring evidence-based repair. An empty stream is valid only when the authoritative source itself reports all counts zero; never use it to replace unknown history. Old partial deletions can leave gaps in part numbers; preserve the actual rows, do not fill gaps or infer an absent part.

After the old executor is verifiably retired, configure the target's `cutover.phase=maintenance`, the same epoch, `interactionFence=I`, `relay.startAfterMessageId=W`, `notificationsAfter` and `legacyWebhooks`. This CONFIG must be deployed to the actual Conversation DOs, not just to the operator. Perform these private RPC steps:

1. `prepare(cut)` validates the entire cut/config before mutations, claims every Directory owner/generation and persists immutable per-conversation history seals. It imports no live effects.
2. `importPage(page)` sends the saved pages in order, **one page per RPC**. Each page's receipts, observed response revisions, digest and checkpoint commit atomically. Retry the identical page after a crash or timeout; changed replay, duplicate Discord ids/natural keys, mismatched source or over-count fails closed.
3. `seal(accountId, conversationId)` checks final digest, page count, all table counts and actual target row counts. It requires the same maintenance epoch and Directory generation. Missing pages never count as complete.
4. `stage(cut)` requires **every** mapping to have sealed history before it marks any ready for activation and stages the digest baseline. Rerun an identical cut after a lost receipt. Obtain all successful receipts; do not activate after any failed claim/import/seal/stage.

Maintenance admits events durably without executing them. A staged but incomplete history also fences execution if someone removes cutover CONFIG or prematurely switches to active. No cleanup or command effects escape that fence. New owners never query the source Hub during online execution.

Set the same cut to active only after every precondition and stage receipt is verified. Request `AccountSweep.request(account,true)` and enqueue every staged conversation (including silent/window-excluded targets) for the first reconcile. Restore sources after the new sole owner is active. Keep the old shell and private evidence during the observation window.

On first use the Conversation rechecks its link and real guild/forum, claims the Directory and runs recoverable history cleanup before making a fresh card. Cleanup pages `limit=100` with persisted `before`/pending deletes. It deletes only an empty-body standalone V2 ticket card of a verified old webhook with the exact ticket-card shape. It never deletes ordinary mirror bodies, even when they have buttons, or another webhook's messages. Individual DELETE accepts a real 404 and retries other failures; it uses no two-week bulk-delete shortcut. Cleanup-complete persists before new card creation. In the final adoption transaction, the target installs W and restores all three nullable title fields without clearing imported receipt tables. Imported pre-W messages are deleted through the bot/channel single-message endpoint, so webhook rotation cannot turn a wrong-webhook 404 into false absence; only confirmed deletion or specific Unknown Message/Channel 404 clears a receipt, and 403/network errors retain it. This requires the verified `MANAGE_MESSAGES` permission ([Discord contract](https://docs.discord.com/developers/resources/message#delete-message)). An UNKNOWN new card stays unaddressable and is never automatically created again; other metadata, mirrors and human commands continue. Register a real resource id only through explicit repair after investigating Discord.

## Preserved history and other boundaries

- Drafts are not imported. A missing/stale draft gives the explicit **Apps → Reply with this** fallback; new cards omit it. Old modal submissions and late answers cannot restore a draft without a current source/generation.
- Hourly counters reset at the next UTC hour. Notifications do not restart the old hour's quota. Digest/escalation baselines have separate handling above.
- Pre-W original/derived receipts and nullable title association/metadata must be imported completely. Deleting their Chatwoot source removes only their authoritative Discord ids; deleting the title source drops its subject, and contact-name changes continue to update recorded titles. Legacy rows whose title was never recorded keep that behavior. This path does not accept historical deletion/title data loss.
- Completeness covers records the source actually owns. A legacy write that succeeded remotely but never recorded a receipt cannot be recovered from similarity or inferred as unsent; unexplained outcomes and unsupported/orphan/conflicting records block the cut. Preserve customer history while obtaining separately reviewed authoritative evidence or repair. Local fixtures never prove real data was repaired.
- Old CSAT/delivery updates are **not frozen**: minimal observed digests are staged, unchanged old updates do not repost, and a genuinely changed old response can still publish. Its newly created receipt supports subsequent deletion. Pending hold semantics are unchanged.
- Old command results cannot be declared uniformly unexecuted merely by dropping their rows. Unexplained prior write outcomes block this cut. New message creation UNKNOWN remains UNKNOWN without history matching or resend.

## Rollback and Hub deletion

Before **any** target business effect or old-card DELETE, an abort can stop new admission/alarms, account for all durably accepted maintenance events/commands, and restore the fully quiesced old executor with those events explicitly handled. Never ACK and silently discard them.

After new DOs have posted or changed Chatwoot, restoring an old snapshot is not clean rollback. Old cursor 100 would repost new 101/102; deleted old cards cannot be restored from SQLite; Chatwoot mutations cannot be undone by restoring DO storage; new durable alarms must be retired before another owner runs. Prefer forward repair in these namespaces. Returning to a Hub requires another stop/drain and explicit checkpoint/effect handover or a newly authorized historical cut and losses. Cloudflare version rollback cannot cross a class-lifecycle change.

After the separately authorized observation window, verify all old routing guards/evidence are accounted for and all old references are gone. `cloudflare.config.ts` mode `retire-hub` uses `src/active.ts` without a Hub export and declares **only Hub** `exports.durableObject({state:"deleted"})`; every partition class remains SQLite. Review its built/prebuilt dry-run lifecycle plan before any authorized deployment. The permanent delete is irreversible; do not claim PITR revives a deleted namespace. Subsequent source cleanup removes the retired shell/inventory control and completed cutover tooling in a separate reviewed change; permanent online effect guards, generation and source boundaries remain.
